# Mini-Spec: Presentation Refactor and Preference Checks for `vacancy_v2`

## Purpose

Refine the presentation and decision architecture of the `vacancy_v2` match pipeline so that:

- the main fit matrix is easier to read and less ambiguous for the user;
- the report no longer rebuilds criterion rows with the LLM;
- comparable vacancy conditions and candidate preferences are evaluated in a more stable way;
- narrative generation remains useful, but no longer acts as the source of truth for table structure.

This spec is intentionally conservative. It does not redesign the entire pipeline. It narrows and hardens the presentation layer.

## Problem Statement

The current `S8 v2` report is directionally useful, but still mixes three concerns that should be separated:

1. criterion adjudication;
2. presentational table assembly;
3. candidate-facing narrative.

That creates three concrete problems:

1. The main table mixes `required_criteria`, `desirable_criteria`, `responsibilities`, `work_conditions` and contextual/company text as if they were the same kind of row.
2. The LLM is currently asked to regenerate table rows that could already be derived from `S6.5`.
3. Preference and condition checks such as location or modality are not yet modeled as a first-class comparable layer.

## Decision Summary

### Decision 1
`S6.5` remains the source of truth for criterion-level alignment.

### Decision 2
The main fit matrix should be assembled deterministically from `vacancy_evidence_adjudication.v1`, not regenerated by `S8 v2`.

### Decision 3
`S8 v2` should generate narrative and recommendation only. It should not decide or rebuild criterion rows.

### Decision 4
Preference checks should be deterministic only after vacancy-side comparable conditions have been normalized. The extraction/normalization of those vacancy conditions may still require interpretation, but the final comparison rule should not.

### Decision 5
The UI should stay conservative:

- `Tipo u origen`
- `Criterio`
- `Estado`
- `Por qué`

Evidence should not be its own wide column. It should appear as an expandable chip or detail inside `Por qué`.

## Existing Data We Can Reuse

The current pipeline already contains most of the information needed for a stronger UI:

### From `S6.5`
- `group`
- `raw_text`
- `alignment_status`
- `evidence_strength`
- `proof_summary`
- `best_supporting_evidence`
- `weak_or_discarded_evidence`
- `limitations`
- `candidate_risk`
- `confidence`

This is enough to build a deterministic criterion matrix.

### From `S7 v2`
- counts by status
- compact strengths
- compact gaps
- review items
- risks

This is enough for summary counters and secondary lists.

### From current profile/opportunity data
- candidate location and structured profile signals
- vacancy raw text
- `work_conditions` raw items
- salary normalization from `S3.1`

This is enough to start a comparable-conditions layer, but not yet enough to make all preference checks deterministic without additional normalization.

## Proposed Architecture

The end-to-end presentation and preference flow should split into six responsibilities:

1. `S6.5` adjudication
2. candidate preference profile cleanup
3. vacancy comparable-condition normalization
4. deterministic preference-check adapter
5. deterministic fit-matrix adapter
6. `S8 v2` narrative

### A. Criterion Truth Layer
Artifact:
- `vacancy_evidence_adjudication.v1`

Responsibility:
- decide whether each criterion is `direct`, `partial`, `indirect`, `not_evidenced`, `conflict` or `not_applicable`
- explain why the supporting evidence does or does not support the criterion

This remains LLM-based and grounded.

### B. Candidate Preference Cleanup Layer
New artifact suggested:
- `candidate_preference_profile.v1`

Responsibility:
- reduce the candidate-side preference model to signals that are actually comparable or contrastable
- separate deterministic-comparison signals from softer company/culture signals

This step should happen before deterministic preference checks.

### C. Vacancy Comparable-Condition Layer
New artifact suggested:
- `vacancy_comparable_conditions.v1`

Responsibility:
- normalize vacancy-side comparable conditions first
- produce explicit comparable values for location, modality, compensation and contract when possible
- preserve uncertainty when the vacancy does not specify a stable signal

This layer may use controlled interpretation, but its output must be normalized and stable.

### D. Deterministic Preference-Check Layer
New artifact suggested:
- `candidate_preference_checks.v1`

Responsibility:
- compare normalized vacancy conditions with normalized candidate preferences or constraints
- return stable `aligned / partial / unknown / conflict` style outcomes

### E. Deterministic Fit-Matrix Layer
New artifacts suggested:
- `vacancy_fit_presentation.v1`

Responsibility:
- derive display rows deterministically from `vacancy_evidence_adjudication.v1`
- group rows for frontend rendering
- avoid asking `S8` to rebuild rows

### F. Narrative Layer
Artifact:
- `vacancy_alignment_report.v2`

Responsibility:
- executive summary
- recommendation
- candidate-facing explanation
- application guidance

This layer should consume deterministic presentation artifacts, not recreate them.

## Why Preference Checks Should Be Deterministic

Deterministic comparison is not the same thing as deterministic extraction.

This distinction matters.

### What should remain interpretive
- extracting ambiguous vacancy signals from messy text
- deciding whether a vague phrase implies location flexibility
- inferring whether a condition was actually specified

### What should become deterministic
- if vacancy location normalizes to `Bogota, Colombia` and candidate location normalizes to `Bogota, Colombia`, the comparison should not depend on another LLM pass
- if vacancy modality is `hybrid` and candidate preference allows `hybrid`, the comparison should not be reinterpreted narratively
- if salary is missing on either side, the output should become `Sin informacion`, not improvisation
- if vacancy is explicitly `remote`, accepted locations should not be used as a blocker and the result should remain compatible even if city-level values differ
- if the candidate has an explicit hard restriction and the vacancy contradicts it, the output should become `En conflicto` without another model pass

So the right architecture is:

1. clean candidate preference profile
2. normalize vacancy comparable conditions
3. compare with explicit rules
4. derive fit presentation deterministically from adjudication
5. let `S8` narrate the meaning of those results

## Profile Cleanup Before Preference Checks

The deterministic layer should not consume the current full preference/profile surface directly.

It should consume a reduced profile containing only:

### Comparable deterministic signals
- current location
- accepted locations
- remote acceptance
- accepted modalities
- salary expectation
- relocation or travel willingness
- explicit hard constraints

These are the signals that `P0` should reduce and normalize for deterministic preference checks.

### Contrastable company-signal preferences
These should remain in profile only if they can later be contrasted against external company signals:
- preferred company types
- regulated vs non-regulated environment preference, when explicit
- leadership-style preference only if framed in observable terms
- collaboration model preference only if framed in observable terms

### Remove from deterministic preference checks
- vague motivators
- broad culture aspirations without observable signals
- abstract red flags that cannot be matched against vacancy/company evidence reliably
- narrative-only preferences with no clear comparison rule

## Enriched Base Candidate Profile

The candidate model should distinguish between:

1. enriched professional profile;
2. comparable preference profile (`P0`).

### Enriched professional profile
This should remain broader than `P0` and should feed:
- `S6.5`
- professional-fit reasoning
- future capability-specific helpers

Recommended fields to keep or add at the base profile level:
- `target_roles`
- `skills`
- `languages`
- `tools_technologies`
- `certifications`

### Minimal suggested shapes

```json
{
  "languages": [
    { "language": "English", "level": "B2" },
    { "language": "Spanish", "level": "native" }
  ],
  "tools_technologies": ["Power BI", "Azure", "SAP"],
  "certifications": ["PMP", "Scrum Fundamentals"]
}
```

### Important separation rule
- `target_roles`, `skills`, `languages`, `tools_technologies` and `certifications` belong to the enriched professional profile;
- they do not belong to `P0` unless a later helper explicitly needs them;
- their existence in profile should not force them into deterministic preference checks.

## Where Languages Fit

Languages and proficiency level are important, but they should not live in the deterministic preference-check layer.

They belong primarily to professional fit:
- vacancy language requirements should be adjudicated as vacancy criteria;
- candidate language evidence should come from core profile and CV evidence;
- if needed later, language can have its own comparable helper, but it is closer to criterion fit than to preference fit.

So:
- `idiomas y nivel` stay in the core candidate profile;
- today they are not yet captured as a first-class structured section in the redesign proposed here, so that capture must be added in the candidate profile model;
- they should remain available for `S6.5` and the professional fit matrix;
- they are not part of the first deterministic preference-check slice.

### Current design decision

- `idioma + nivel`: yes in candidate profile
- `idioma + nivel`: not in `P0`
- language contrast: inside the main professional-fit flow
- if later we want a stricter comparison, it should be implemented as a capability-specific helper, not as a preference check

### Suggested minimal shape

```json
[
  { "language": "English", "level": "B2" },
  { "language": "Spanish", "level": "native" }
]
```

### Scope note

The same reasoning may later apply to:
- certifications
- tools and technologies

Those fields should be captured in the enriched professional profile, but they are not part of the current `P0` comparison slice.

## Frontend Presentation Spec

## Main Matrix

The main fit matrix should not be a single undifferentiated list.

It should be rendered in grouped sections:

1. `Requisitos obligatorios`
2. `Responsabilidades`
3. `Deseables`

Optional later:

4. `Condiciones de la vacante`

`about_the_company` should not appear in this matrix.

### Recommended columns

Keep the table conservative:

1. `Tipo u origen`
2. `Criterio`
3. `Estado`
4. `Por qué`

### Column semantics

#### `Tipo u origen`
Expected user-facing values:
- `Obligatorio`
- `Responsabilidad`
- `Deseable`
- `Condicion`

This should come deterministically from `group`.

#### `Criterio`
Display:
- `raw_text`

#### `Estado`
Display mapping from adjudication:
- `direct` -> `🟢 Cumple`
- `partial` -> `🟡 Parcial`
- `indirect` -> `🟡 Parcial`
- `not_evidenced` -> `⚪ Sin informacion`
- `conflict` -> `🔴 En conflicto`
- `not_applicable` -> hidden from main matrix unless explicitly needed

For desirable items only:
- `not_evidenced` may display `🔵 Deseable no evidenciado`

#### `Por qué`
Base text:
- `proof_summary`

Secondary content inside the same cell:
- chips for `Fortaleza`, `Parcial`, `Indirecta`, `Sin evidencia`, `Conflicto`
- chip `Ver evidencia (N)` opening an inline panel or details drawer
- optional chip `Limitaciones`

Expanded evidence view should show:
- `source_ref`
- `block_title`
- `section`
- `snippet`
- `why_it_supports`

Weak evidence may appear under a secondary expandable area:
- `Evidencia descartada`

## Candidate Preference Matrix

This should be a separate block, not mixed with the main fit matrix.

Suggested sections:

1. `Ubicacion y modalidad`
2. `Compensacion`
3. `Condiciones relevantes`

Recommended columns:

1. `Criterio`
2. `Estado`
3. `Vacante`
4. `Perfil`
5. `Por qué`

The matrix should support:
- `🟢 Cumple`
- `🟡 Parcial`
- `⚪ Sin informacion`
- `🔴 En conflicto`

## How the Deterministic Layer Operates

The deterministic layer is a rule engine over normalized inputs. It does not infer new meaning. It compares already-normalized values.

### Example 1: Location

Inputs:
- vacancy comparable condition: `Bogota, Colombia`
- candidate preference profile: current location `Bogota, Colombia`

Rule:
- normalized city and country match -> `🟢 Cumple`

If vacancy is `remote`:
- state remains compatible regardless of city mismatch, unless another hard restriction applies

If vacancy location is missing:
- `⚪ Sin informacion`

### Example 2: Modality

Inputs:
- vacancy modality: `hybrid`
- candidate accepted modalities: `hybrid`, `remote`

Rule:
- vacancy value inside accepted candidate set -> `🟢 Cumple`

If vacancy says `onsite` and candidate profile says `remote only`:
- `🔴 En conflicto`

If vacancy modality is ambiguous:
- `⚪ Sin informacion`

### Example 3: Salary

Inputs:
- vacancy normalized salary
- candidate salary expectation

Rule:
- comparable overlap or sufficient compatibility -> `🟢` or `🟡`
- missing numeric basis on either side -> `⚪`
- explicit contradiction with hard expectation -> `🔴`

### Example 4: Narrative Does Not Re-Decide

If the deterministic layer yields:
- `location -> 🟢`
- `modality -> ⚪`
- `salary -> 🟡`

Then `S8` may explain the implications, but it must not convert those rows into a different state.

## Narrow Extension Proposed for `S3.1`

Current `S3.1` salary normalization keeps the fixed salary shape and preserves the rest inside `raw_text`.

That is not enough when the vacancy says things like:
- `$12.000.000 + comisiones`
- `base salary + variable bonus`

Recommended narrow extension:

```json
{
  "salary": {
    "min": 12000000,
    "max": null,
    "currency": "COP",
    "period": "monthly",
    "raw_text": "$12.000.000 COP + comisiones",
    "has_variable_component": true,
    "variable_component_type": "commission",
    "variable_component_note": "comisiones"
  }
}
```

Rule:
- `min/max/currency/period` continue representing only the fixed comparable salary base;
- the variable component is preserved explicitly so later preference checks can say:
  - fixed salary is comparable;
  - plus there is variable compensation.

This is preferable to leaving commissions only inside `raw_text`.

## 3. `candidate_preference_checks.v1`

Purpose:
- compare normalized vacancy conditions with normalized candidate preferences and constraints

Suggested shape:

```json
{
  "contract_version": "candidate_preference_checks.v1",
  "vacancy_id": "string",
  "person_id": "string",
  "generated_at": "datetime",
  "rows": [
    {
      "criterion_key": "location",
      "criterion": "Ubicacion",
      "state": "🟢 Cumple | 🟡 Parcial | ⚪ Sin informacion | 🔴 En conflicto",
      "vacancy_value": "Bogota, Colombia",
      "candidate_value": "Bogota, Colombia",
      "why": "La ubicacion declarada de la vacante coincide con la ubicacion actual del candidato.",
      "confidence": "high"
    }
  ],
  "warnings": []
}
```

Comparison rules should be deterministic:
- exact compatible match -> `🟢`
- compatible but weaker or incomplete signal -> `🟡`
- missing signal on vacancy or candidate side -> `⚪`
- explicit contradiction with hard constraint -> `🔴`

## Changes to `S8 v2`

`S8 v2` should be narrowed.

### Keep in `S8 v2`
- `executive_summary`
- `decision_table`
- `fit_answer`
- `strengths`
- `gaps`
- `preference_conflicts`
- `improvement_actions`
- `alerts_and_conflicts`
- `actionable_conclusion`
- `rendered_markdown`

### Remove from `S8 v2` generation responsibility
- `vacancy_fit_matrix`
- `candidate_preference_matrix`

These should be assembled deterministically before or outside `S8`.

### Short-term compatibility option

To avoid breaking the current UI immediately:

1. keep `vacancy_alignment_report.v2` contract temporarily;
2. mark `vacancy_fit_matrix` and `candidate_preference_matrix` as backend-injected deterministic sections;
3. let the LLM generate only the narrative fields;
4. deprecate matrix generation inside the prompt.

This is the recommended migration path.

## Execution Order

Recommended runtime order:

1. `S1 -> S2 -> S3 -> S3.1 -> S3.9 -> S4 -> S5 -> S6 -> S6.5 -> S7 v2`
2. `P0` candidate preference cleanup
3. `C1` vacancy comparable-condition normalization
4. `C2` deterministic candidate preference checks
5. `P1` deterministic fit presentation from `S6.5`
6. `S8 v2` narrative and recommendation

Notes:
- `P0` is candidate-centric and may be recomputed when profile changes, not only when vacancy changes;
- `idiomas + nivel` live in the core candidate profile and feed professional fit, but they are outside `P0`;
- `P1` and `C2` are sibling presentation inputs for `S8`, not parent/child replacements of each other;
- `S8` should consume both and explain them, not rebuild them.

Backend:
- create `candidate_preference_profile.v1`
- keep only comparable and contrastable preference signals

Frontend:
- expose this reduced profile clearly in the profile section

Acceptance:
- deterministic preference checks no longer depend on noisy preference fields

## Slice A — Deterministic fit matrix from `S6.5`

Backend:
- create `vacancy_fit_presentation.v1`
- build adapter service from `vacancy_evidence_adjudication.v1`
- persist artifact per opportunity
- expose recompute endpoint

Frontend:
- replace current single `vacancy_fit_matrix` rendering with grouped deterministic rendering
- columns: `Tipo u origen`, `Criterio`, `Estado`, `Por qué`
- add expandable evidence chip inside `Por qué`

Acceptance:
- no LLM needed to render matrix rows
- all adjudicated items appear exactly once, except intentionally excluded groups

## Slice B — Comparable vacancy conditions

Backend:
- create `vacancy_comparable_conditions.v1`
- normalize location, modality, compensation and basic contract signal

Frontend:
- expose read-only JSON in experimental panel

Acceptance:
- `Bogota D.C.` and `Bogota, Colombia` can converge to the same comparable location form
- missing condition stays missing
- `salary + commissions` no longer hides the variable component only in `raw_text`

## Slice C — Deterministic preference checks

Backend:
- create `candidate_preference_checks.v1`
- compare candidate-side structured preferences/constraints with vacancy comparable conditions

Frontend:
- render separate preference matrix

Acceptance:
- no LLM needed to decide row state
- explicit unknown remains `⚪ Sin informacion`
- hard conflicts become `🔴 En conflicto`
- remote vacancy can remain compatible without forcing a city-level match

## Slice D — Narrow `S8 v2`

Backend:
- reduce `S8 v2` prompt so it no longer generates fit-matrix rows
- inject deterministic matrix sections into final report payload if contract compatibility is needed

Frontend:
- continue showing executive summary and markdown
- source matrix views from deterministic artifacts, not from `S8` text generation

Acceptance:
- `S8` can fail less often due to row omission
- matrix completeness no longer depends on LLM obedience

## Slice E — UI readability improvements

Frontend:
- grouped matrix sections
- evidence panel within `Por qué`
- separate block for preference checks
- clearer labels for `Obligatorio`, `Responsabilidad`, `Deseable`, `Condicion`

Acceptance:
- user can tell what is a requirement, a desirable, or a responsibility without reading raw criterion text carefully
- evidence is inspectable on demand without widening the table

## Risks

### Risk 1
Adding too many new artifacts increases implementation spread.

Mitigation:
- start with `vacancy_fit_presentation.v1`
- then add vacancy comparable conditions
- then add preference checks

### Risk 2
Vacancy comparable conditions may still be weakly defined in the source text.

Mitigation:
- preserve `confidence`
- preserve `warnings`
- use `Sin informacion` when normalization is not trustworthy

### Risk 3
Temporary duplication between `S8 v2` and deterministic presentation artifacts.

Mitigation:
- treat the duplication as transitional
- retire matrix generation from `S8` once frontend consumes deterministic artifacts

## Recommended Order

1. implement candidate preference cleanup
2. implement deterministic fit matrix from `S6.5`
3. refactor frontend table presentation
4. implement vacancy comparable conditions
5. implement candidate preference checks
6. narrow `S8 v2` to narrative-only

## Final Recommendation

Do not keep patching `S8 v2` as the owner of tabular structure.

The best result comes from this split:

- `S6.5` decides criterion alignment
- deterministic adapters assemble matrices
- preference checks compare normalized comparable conditions
- `S8 v2` explains and recommends

This keeps the best part of the LLM where interpretation is needed, and removes it from the part where structural consistency matters most.
